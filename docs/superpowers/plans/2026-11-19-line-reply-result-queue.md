# LINE Reply Result Queue Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans for native implementation, preserving the user's established execution preference. Implement task-by-task; request one final read-only review before rollout.

**Goal:** Reply to commands immediately and deliver durable import/publication terminal results FIFO on the originating allowed group's next message, without push fallback.

**Architecture:** D1 stores terminal result bundles separately from business jobs and coordinates a single reply dispatch per incoming event. One composer owns each reply token, combines the command response with at most one queue head, and fences the external send before calling LINE. Import/publication workflows persist results in dedicated notification steps after their business finalization.

**Tech Stack:** Existing TypeScript, Zod, Cloudflare Workers/Workflows, D1 and Vitest; no new dependency or service.

**Spec:** `docs/superpowers/specs/2026-11-19-line-reply-result-queue-design.md` (approved 2026-11-19).

## Global Constraints

- Preserve `/upload` and `/docs` first-message wording and Flex content exactly; add no queue explanation.
- All immediate command/button responses use Reply API; no push fallback or push retry notices. Postbacks do not drain results.
- One oldest final-result bundle per incoming message, same allowed group only. Command response first; maximum five message objects; bundles are indivisible.
- Support ordinary text and non-text message triggers without persisting their content or fetching media. Never fabricate an actor ID.
- Business outcome and notification outcome are independent. Queue/send failure never repeats business writes or downgrades successful work.
- Quiet groups retain results. No cron, automatic expiry, backfill, private chat, new Settings UI or status command.
- Unknown outbound acceptance is held for investigation, never automatically replayed. An unresolved head blocks later queue results, not normal commands.
- Existing credentials, permissions, business retry limits, messenger layout, original-group contexts and asset access controls stay intact.
- This plan authorizes local implementation only. A remote migration, deployment, live group message, or manual dispatch repair requires separate rollout authorization.

## Review Focus

- A source event without a user ID can drain a group result but cannot execute `/soldout`, messenger completion or another actor-dependent command: Task 4 tests.
- A command reply already contains five objects, or a queue reservation loses a race: the command still replies once and the result stays available: Tasks 1/3/4 tests.
- A worker dies between reservation, dispatch fencing, LINE acceptance and receipt persistence: only provably unsent reservations can be released: Tasks 1/3 tests.
- Publication failure recording itself fails (as in the current Google OAuth incident): retain notification intent without claiming cleanup/finalization succeeded: Task 5 tests.
- A delayed result crosses midnight or a base change: keep original run/date/group/URLs, recheck current allowed-group membership, never rebuild from new inventory: Tasks 2/5/6 tests.

## Shared contracts

Define these contracts in Tasks 1–3 and use the same names in later tasks:

- `LineReplyMessage = { type: "text" | "flex" | "template"; [key: string]: unknown }`. Validate supported top-level required fields and existing limits before dispatch; reuse existing builders for nested content.
- `TerminalResultV1 = { schemaVersion: 1; kind: "import" | "publication"; runId: string; generation: number; notificationCycle: number; outcome: "success" | "partial" | "validation_failed" | "failed" | "unconfirmed"; messages: LineReplyMessage[] }`.
- `enqueueResult(input: { resultKey: string; groupId: string; result: TerminalResultV1 }): Promise<void>`. Result key is JSON encoding of `[kind, runId, generation, notificationCycle, "terminal"]`, independent of outcome and destination. A replay with identical content is a no-op; conflicting destination/content is an error, never an overwrite.
- `renderCommandReply(reply: CommandReply, publicBaseUrl: string): LineReplyMessage[]` preserves all currently rendered variants.
- `sendReplyMessages(replyToken: string, messages: LineReplyMessage[]): Promise<{ requestId: string | null }>` on `LineClient`; uses `/message/reply`, never `X-Line-Retry-Key`.
- `deliverEventReply(input: { eventId: string; groupId: string; workflowId: string; receivedAt: string; replyToken: string; commandReply: CommandReply | null; drainQueue: boolean; publicBaseUrl: string }, deps): Promise<"accepted" | "rejected" | "uncertain" | "ignored" | "duplicate">`.

Do not persist `replyToken` in result or dispatch tables. A reply token remains only in the existing private Workflow event payload, consumed during the live attempt. No raw incoming conversational content goes in those tables either.

`prepareDispatch({eventId,groupId,workflowId,receivedAt,candidateSequence:number|null,messages:LineReplyMessage[]})` returns `"prepared" | "duplicate" | "head_changed"`. `head` returns the oldest non-accepted row including its state, or null; callers cannot bypass a blocked head. `beginDispatch` returns a CAS boolean. `reject` disposition is `"retry_on_new_event" | "blocked_payload" | "blocked_configuration"`.
