# Recoverable results for /docs and /upload

Draft for approval · 20 November 2026

## Staff experience

After an authorized LINE command, staff should be able to tell what happened, which work is safe to keep, and who should do what next. A stale Airtable status should never be the sole reason staff cannot generate a document. Recovery must protect a completed document or an imported product even when its confirmation failed.

Keep the existing start cards and the [group reply queue contract](2026-11-19-line-reply-result-queue-design.md). Reply immediately to the command when possible. On a known refusal before a job starts, explain the reason in that reply. When a job starts, retain its result for the originating group's next eligible message, oldest queued first. A quiet group can wait indefinitely. No new commands, push fallback, cron, or change to the business retry limits is required.

### What a result says

Use a compact Thai Flex card, with a plain-text equivalent when rendering fails. Lead with the outcome, identify the run by its original date and a stable reference, then give one useful action. Link to the verified document or the relevant Airtable record when available. Show a product ID and field name for data errors. Bound long lists and retain full details for the owner. Distinguish staff actions from owner actions. Show provider-specific reasons only when confirmed. Never send tokens, raw provider responses, customer data from logs, or stack traces in LINE.

A known original failure and an unknown cleanup result can be shown together. Label an earlier queued result with its original run/attempt so it is distinguishable from a new start card.

## Proposed approach

Smallest sufficient design: reuse the existing D1 job, group, execution-context, and LINE outbox records. Persist the business outcome independently of cleanup, Airtable status synchronization, and LINE delivery. Reconcile on existing entry points. A wider catch would improve feedback but could still leave Airtable blocking every subsequent command. A scheduled sweeper could repair idle groups sooner but would add background work and still need the same reconciliation rules.

Each accepted command needs durable originating group, event and run identity before an external effect, including a publication generation and notification cycle where applicable. Record the stage reached, first actionable failure, verified output references, unresolved side effects and required repairs. Save enough immutable result data to reconstruct feedback without querying current settings or replaying provider calls. Use a single D1 transaction for dependent local writes or persist a recoverable intent before crossing a service boundary. Reuse existing keys and captured configuration. The implementer chooses schema details.

Cloudflare establishes execution liveness. D1 establishes ownership and recorded progress. Google, R2 and Airtable establish the external effects they own. A stopped Workflow can have produced a valid document. A failed notification can accompany a successful import. On conflicting evidence, preserve verified work, record what remains unknown, and withhold destructive changes or new creation until reconciled.

## Failure and acceptance matrix

Each numbered case is a required regression scenario. Inject failure on the indicated boundary, recover through a normal entry point, and verify both the staff response and durable state.

Separately, job starts and initial LINE reply fails. | Use the event and intended Workflow ID to find the execution before creating again. Confirm a start only with evidence. If definitively refused, explain immediately when the token is usable. Otherwise retain an identifiable unresolved command. A lost start reply never cancels the final result. |
| 2 · Early setup | Settings snapshot, publication notification identity, or dependency setup fails before the business handler. | Record the stage from the accepted command identity. ## Rules for choosing a safe next action

- An immediate command reply can report a refusal or that verification is pending. A pre-start refusal with a confirmed reply needs no second card. A later eligible event can carry a missed definitive result only if the accepted command and origin were durably recorded and non-delivery is established.
- Keep the existing one-running-import-per-album constraint. Before treating its lock as live, inspect the owning run and its Workflow. For a stopped import, resolve the captured snapshot and outstanding groups first. If a staff retry cannot select a failed historical group, point to owner re-import recovery. A new scan can include newly added photos only as new work.
- For publication, a Failed record with verified absence of unsafe effects can follow the existing explicit restart path. Ready after a successful generation remains an explicit regeneration request. If an observed manual change conflicts with a pending repair, re-read immediately before writing and hold the repair where the intended transition cannot be established. Write only system-owned status/output fields for that attempt. Keep the previous successful document available until its replacement is verified.
- A request in a different allowed group can receive a generic busy response for shared work. It cannot claim that run's result, receive its private diagnostics, or change its destination. Owner repair must use the captured provider target. A credential or base change that prevents identifying the original target leaves the run on hold.

## When reconciliation happens

- At Workflow exit, persist the outcome and notification intent before fallible cleanup or status projection. If a provider operation itself has an unknown outcome, record the uncertainty and its evidence. Retry bookkeeping independently within existing persistence limits.
- Before answering the next matching /docs or /upload, check outstanding work for the original target and owner. In particular, check Generating before the publication trigger's early return. If external verification exceeds the reply window, immediately reply “กำลังตรวจสอบงานเดิม” with the owning group’s reference and defer verification. This command requests a check only. After receiving its result, staff can explicitly start a new attempt when safe. For a live owner, report already running. For proven failure with no outstanding unsafe effects, repair stale status and permit the existing retry flow. For a verified output, return it. For ambiguous effects or unavailable evidence, return the reference and safe next action, without starting another job.
- On the next eligible group message, perform bounded local repair of missing result entries before queue selection. Use an indexed lookup for the originating group; keep provider discovery off the reply-token path. For an interrupted run needing external verification, arrange a deduplicated recovery check through the existing Workflow mechanism. Its result may arrive on a later eligible message. Cap repair work so a backlog cannot consume the command reply window.
- For an ambiguous run, persist a reviewable result once. If later verification changes what staff should do, retain the original dispatch history. Queue one clearly labeled correction tied to the same run with a distinct stable result identity. Replay of the repair produces no extra corrections. A newer correction never jumps an unresolved older queue head.
- Owner recovery must be available through a documented authenticated procedure using existing tooling. By run reference, inspect captured target, execution state, original failure, provider references, sync/cleanup state, queue head and dispatch evidence. Allow scoped repair of verified state or missing notice, with a recorded disposition. For uncertain delivery, require an explicit owner decision to resolve the head; distinguish confirmed acceptance from an owner choosing to close an unverifiable send. Never automatically resend it. Restrict evidence to the owning context and keep secrets out of logs.

## Compatibility, verification and release

Use additive storage changes and tolerate existing running, completed, pending and legacy jobs. Recover legacy work only when the saved evidence identifies the target, owner and effect. Otherwise expose an owner-review reference. Preserve settings snapshots, group allowlists, existing queue order, historical results and previously generated files. Recovery must work after a process restart. If an eligible event cannot be durably accepted during a D1 outage, return a retryable webhook failure before acknowledging the request. Deduplicate already accepted events if the batch is redelivered. LINE redelivery is conditional; record a sanitized ingress error for owner diagnosis. Use an immediate safe reply only where event ownership and routing can still be verified. A total loss of both persistence and LINE access precludes guaranteed feedback for that event.

Before rollout, run the 15 scenarios against both applicable entry points, including duplicate/concurrent repair, cross-group isolation and configuration changed since capture. Verify counts, links, queue order, owner fencing, number of provider creations and actual next-command behavior. Include a staging exercise with a forced cleanup failure and stale Generating row, and a mixed import interrupted after Airtable creation. Confirm existing legitimate regeneration, empty imports and unchanged start cards. A rollout plan must preserve outstanding records during rollback. Implementation and staging deployment require separate approval.
